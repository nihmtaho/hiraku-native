Read `PROJECT.md` at the repo root first. If it is missing, stop and ask the user to
create it from the kit's `PROJECT.md.example`.

You change a contract. The contract source named in `PROJECT.md` §Architecture rules
is the single source of truth; generated code is derived from it and is never edited
by hand.

## Input and sources

Receive the task packet: base revision, the behavior to change, and the baseline
contract. Paths are relative to the repository root, not the skill directory.

Read the contract sections of the architecture rules file named in `PROJECT.md`
§Architecture rules, the decision records it names, and the spec and use-case sections
for the task. An open decision on error codes or business behavior that affects the
task: report BLOCKED before choosing a schema.

## Workflow

1. List the messages and methods, callers and receivers that change. Decide
   compatibility, error mapping, time handling, transactions, and change sets. Keep
   every fact on the side of the boundary `PROJECT.md` §Architecture rules defines;
   the contract layer must not learn about UI-only infrastructure.
2. Edit the contract source named in `PROJECT.md` §Architecture rules. Add new field,
   method, and enum numbers; never reuse one already used. When dropping a field,
   reserve it per the project's contract convention.
3. Run the lint, generator, and breaking-change commands in `PROJECT.md` §Checks.
   Read the tool configuration to run the right directory; do not guess the main file
   or an empty baseline. The first contract must state that no baseline exists — never
   report a fake breaking-change pass.
4. Put pure logic in the layer your architecture names for it and coordination and
   transactions in the layer above it; wire dispatch through the boundary the
   architecture rules define. Keep panic protection and handle ownership at your
   FFI/bridge entry points (if any); never invert the dependency direction (the logic
   core calling the UI, or the UI opening the database itself).
5. Connect the contract to the model and error types, protocols, and test fakes named
   in `PROJECT.md` §Architecture rules, and move the callers onto the new interface.
   Emit change events with the scope the architecture defines.
6. Add or update shared golden contract fixtures and tests on both sides for success,
   failure, and compatibility cases. A golden change must explain the behavior it
   captures; never regenerate only to hide a regression. Never hand-edit generated
   files or directories.
7. Run the checks in `PROJECT.md` §Checks that cover the changed layers and the
   integration between them; if the ABI or build output changed, verify the real
   artifact. Record the command, environment, and result for each side.
8. Update the spec, use cases, and design documents (paths per `PROJECT.md` §Docs map)
   when behavior changes. A breaking change needs its migration plus fixture and golden
   updates in the same branch before merge, and PO approval of a decision record first.

## Handoff and stop conditions

Return a table: changed surface → file → check → result; plus baseline, revision,
golden files touched, and compatibility risks. A missing tool, generator, baseline,
fake, or required test: state BLOCKED/PARTIAL explicitly. Never hand-write a payload
in place of the contract to get past it.

If you are reviewing: use the steps as a read-only checklist; do not run generators,
change golden files, or edit source. Verdict per `flow-review`.

## Limits

- Checks not run or skipped are recorded as `Not run`; never report them as passed.
- No "Generated by AI", co-author, or robot markers in commits or PRs.
- Never read signing or credential secrets (`.env*` except `.env.example`, `*.p8`,
  `*.p12`, `*.pem`, `*.key`).
