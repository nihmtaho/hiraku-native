# Flowkit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` (recommended) or `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Flowkit portable skills kit in `.tmp/flowkit/` — 10 generic `flow-*` process skills ported 1:1 from hiraku, 8 PM skills adapted, 2 new skills, profile mechanism, portable harness template, and a self-check script that proves the kit is clean.

**Architecture:** Profile-driven 1:1 port. Skills live in `.tmp/flowkit/skills/<name>/SKILL.md`, read `PROJECT.md` at the consumer repo root for all project-specific facts, and contain zero hiraku references. `scripts/check-kit.mjs` is the acceptance test.

**Tech Stack:** Node.js 24+ (no dependencies), Markdown, git.

**Spec:** `docs/plans/2026-11-09-portable-skills-kit-design.md` (approved 2026-11-09). The plan argues from the spec; executors read both.

## Global Constraints

- **Output root:** `.tmp/flowkit/` inside this worktree. Committed to this branch (approved exception to the root-files rule; noted in README).
- **Language:** all kit content English. The 10 hiraku source skills are Vietnamese — porting includes translating to English.
- **Skill format:** directory + `SKILL.md`, frontmatter with `name` and `description` (keep `compatibility` when the source has it; drop `argument-hint`).
- **Skill mapping (1:1):** `hiraku-coordinator`→`flow-coordinator`, `hiraku-task`→`flow-task`, `hiraku-coding`→`flow-implement`, `hiraku-create-pr`→`flow-pr`, `hiraku-review`→`flow-review`, `hiraku-ship`→`flow-ship`, `hiraku-wp-status`→`flow-status`, `hiraku-contract`→`flow-interface`, `hiraku-feature`→`flow-feature`, `hiraku-spike-report`→`flow-spike`.
- **Transformation rules** (apply to every ported skill; source = `.agents/skills/hiraku-*/SKILL.md` in this worktree):
  - T1: skill name references → new `flow-*` name (paths like `.agents/skills/hiraku-x` → `flow-x`).
  - T2: repo file paths (`.agents/tasks/`, `.agents/templates/`, `docs/process/*`, `ROADMAP.md`, `CHANGELOG.md`, `ARCHITECTURE.md`, `DECISIONS.md`) → pointer to the matching `PROJECT.md` section (§5.2 of spec: Status tracking / Git & PR / Checks / Docs map / Architecture rules / Quality rules).
  - T3: hiraku identifiers (`WP-xx`, `Q-xx`, `ADR-xx`, `M-xx`, `S-x`, gate names) → generic wording ("open decision", "milestone", "checkpoint per PROJECT.md §Status tracking"). Never keep the identifier.
  - T4: concrete commands (`go test`, `xcodebuild`, `check-core.sh`, `buf lint`, `task-context.mjs`, `wp-status.mjs`) → "run the commands in PROJECT.md §Checks" / "§Status tracking".
  - T5: keep every guardrail verbatim in behavior: verdict PASS/FAIL/BLOCKED on exact head SHA; independent review in a fresh subagent, never self-review; at most one senior at a time; `--force-with-lease` only on the task branch; no force to base; no "Generated by AI"/robot in commits or PRs; never read secrets (`.env*` except `.env.example`, `*.p8`, `*.p12`, `*.pem`, `*.key`); never report PASS/merged before checks ran; `Not run` when a check wasn't run.
  - T6: every `flow-*` skill body must contain the string `PROJECT.md` (opening line: read `PROJECT.md` first; if missing, stop and ask the user to create it from `PROJECT.md.example`).
- **PM source (absolute path, archive is NOT in this worktree):**
  `/Users/nihmtaho/developer/repos/per-projects/hiraku-native/docs/archive/Product Management-1.2.0-v1/skills/<name>/SKILL.md`
  Adaptations: drop `argument-hint`; drop `$ARGUMENTS` command blocks and `/command` usage sections; replace `CONNECTORS.md` references with "provide context manually when no connector is available"; otherwise keep content verbatim.
- **PM license:** copy `/Users/nihmtaho/developer/repos/per-projects/hiraku-native/docs/archive/Product Management-1.2.0-v1/LICENSE` → `.tmp/flowkit/LICENSE.pm-skills`.
- **Forbidden tokens in `.tmp/flowkit/skills/**`** (enforced by `check-kit.mjs`): case-insensitive `hiraku`; case-sensitive `ROADMAP`, `DECISIONS`, `WP-`, `$ARGUMENTS`, `CONNECTORS.md`, `task-context`, `wp-status`. If a PM skill trips one (e.g. uppercase `ROADMAP`), reword to the generic lowercase term — that is an allowed adaptation.
- **Commits:** after every task, Conventional Commit in English, no AI co-author/trailer (skill `git-commit`).
- **Not in scope:** touching `.agents/skills/`, opening a PR, CHANGELOG/ROADMAP/Kanban ritual (deferred until PO asks to ship).

## Review Focus

1. **Forbidden-token detection actually works** (case rules differ: `roadmap` the word is legal, `ROADMAP` the file is not) — Task 1 injects a deliberately bad skill fixture and asserts the script reports it, then removes the fixture.
2. **Claude-isms survive in PM ports** (`$ARGUMENTS`, `CONNECTORS.md`, `/command` blocks) — forbidden tokens in `check-kit.mjs` (Task 1); Task 6 runs the check as its gate.
3. **Ported skills still reference dead hiraku scripts** (`task-context.mjs`, `wp-status.mjs`) — same forbidden list; Task 2–4 gates run the check after each batch.

**Files:**
- Create: `.tmp/flowkit/skills/flow-debug/SKILL.md`
- Create: `.tmp/flowkit/skills/product-review/SKILL.md`

**Interfaces:**
- Consumes: skill format + T6 (both mention `PROJECT.md`).
- Produces: `flow-debug` (debugging workflow), `product-review` (spec/design/product review, read-only, findings by severity).

- [ ] **Step 1: Write `flow-debug/SKILL.md`** (~40 lines, English):
  1. Reproduce first; record the exact command/output. No fix without a reproduction (or a written reason it can't be reproduced).
  2. Gather evidence; narrow the search space; hypothesize before editing.
  3. Find the root cause in shared code — fix once, never patch every caller.
  4. Smallest fix; add a regression test that fails before the fix and passes after.
  5. Never "fix" by deleting tests, disabling checks, or swallowing errors.
  6. Run the smallest relevant check; record command + exit code.

- [ ] **Step 2: Write `product-review/SKILL.md`** (~40 lines, English):
  - Review a spec/PRD/design read-only (never edit during review).
  - Checklist: real problem with evidence; goals/non-goals clear; scope not over-built; success metrics measurable; acceptance criteria complete; risks/dependencies listed; design serving stated user goals, consistent with existing product docs, accessibility expectations noted (link skill `accessibility` if installed).
  - Findings by severity: **blocker / should-fix / suggestion**, each with location and why.
  - Output: verdict `READY` or `CHANGES NEEDED` + findings. No file edits.
