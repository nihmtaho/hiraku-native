name: flow-implement
description: >-
  Senior implements a task that already has a task record: changes code within scope,
  adds behavioral tests, updates documentation, changelog and status on the task
  branch, then commits and pushes. Use when handed a task to code, when fixing review
  findings, or when continuing an unfinished task.
compatibility: Git; the language toolchain named in PROJECT.md; run from the repository root.
---

Read `PROJECT.md` at the repo root first. If it is missing, stop and ask the user to
create it from `.agents/PROJECT.md.example`.

You implement a task packet. Read the task record and the architecture rules file named
in `PROJECT.md` §Architecture rules, including its relevant sections. If the project has
an `AGENTS.md`, read it before editing code.

## Workflow

1. Missing task record, or an unresolved open decision that affects behavior: return
   `BLOCKED`; do not guess.
2. Check Git state: branch, working tree, pre-existing changes. Do not overwrite work
   that is not yours. If the task branch already exists, continue on it.
3. If there is no branch yet: create `<type>/<task-id>-<short-summary>` from the base branch named in
   `PROJECT.md` §Git & PR. Mark the work item in progress with `flow-status` (states
   per `PROJECT.md`).
4. Interface/contract change: load `flow-interface`. New feature: load `flow-feature`.
   Spike: load `flow-spike`. Anything else: read the documents directly; do not create
   a new abstraction layer.
5. Choose the simplest solution that fully meets the requirements. Follow
   `PROJECT.md` §Architecture rules: keep each concern on its side of the module
   boundaries, never hand-edit generated files or directories, and resolve names by
   the roles the architecture defines instead of hard-coding them.
6. Add behavioral and failure-case tests. Run the smallest check in `PROJECT.md`
   §Checks that covers the change; widen it when you touch an interface. Record the
   command and exit code.
7. If behavior changes, update the spec, use cases, and design documents together
   (paths per `PROJECT.md` §Docs map). In the same branch: add a `[Unreleased]` line
   to the changelog named in `PROJECT.md`, and update the work-item state with
   `flow-status` per `PROJECT.md` §Status tracking.
8. Small commits, per the `git-commit` skill. No `--amend`, no `--no-verify`.
   Push: `git push -u origin <type>/<task-id>-<short-summary>` (branch naming per `PROJECT.md` §Git & PR).
9. Fixing review findings: fix within scope, commit anew, push. If a rebase is needed:
   `git rebase <base-branch>`, then `git push --force-with-lease origin <task-branch>`
   (both per `PROJECT.md` §Git & PR). Only on the task branch; never force-push to the
   base branch or `main`; never a bare `--force`.
10. Update the task record: state, revision, changed files, commands run with their
    exit codes.

## Code quality

- Simplest change that fully solves the task; no abstraction "for later"; no
  speculative features.
- Only touch what the task requires; short functions, early returns, max 3 nesting
  levels.
- Use the standard library and platform frameworks first; reuse existing helpers the
  way surrounding code does.
- Comments: one line, English (or the language named in `PROJECT.md` §Quality rules),
  explaining *why* only; never restate code; no long blocks. Exception:
  `// TODO(<id>): …`.
- No leftover `print`/debug logging, dead code, unused imports.
- Tests: behavioral, short, one assertion theme each; run the smallest check covering
  the change, record the command and exit code.
- New non-trivial logic (branch, loop, parser, money/security path) leaves one small
  test.

## Limits

- Do not open the PR (that is `flow-pr`'s job), do not merge, tag, or release; never
  read signing or credential secrets (`.env*` except `.env.example`, `*.p8`, `*.p12`,
  `*.pem`, `*.key`).
- Do not edit CI, the checker, `AGENTS.md`, the workflow documents listed in
  `PROJECT.md` §Docs map, or the decision records in `PROJECT.md` §Architecture rules.
  Do not edit golden files or released migrations just to make tests green.
- New dependencies or open decisions: ask the coordinator or PO before installing or
  applying them.
- Checks not run or skipped are recorded as `Not run`; never report PASS.
- Tests and builds run repository code; never use release credentials or the network
  outside the permitted scope.
- No "Generated by AI", co-author, or robot markers in commits or PRs.

## Output

`IMPLEMENTED`, `PARTIAL`, or `BLOCKED`, with task ID, branch and SHA, changed files,
criteria met, commands and exit codes, unverified parts, and decisions needed. Never
claim merged yourself.
